## 🐛 根本原因

**问题：WhisperX返回的时间戳和音频时长不一致！**

### 原因分析

查看WhisperX返回的JSON：

```python
# whisperx_align.py 返回
{
    "chars": [
        {"char": "你", "start": 0.000, "end": 0.121},
        {"char": "喜", "start": 0.121, "end": 0.221},
        ...
        {"char": "？", "start": 1.046, "end": 1.066}  <- 最后字符
    ],
    "duration": 1.378  <- 音频总时长（从FFmpeg获取）
}
```

**发现：**
- `duration`: 1.378秒 - 这是音频文件的实际时长（FFmpeg读取）
- 最后字符end: 1.066秒 - 这是WhisperX识别到的最后一个字符的结束时间
- 差异：1.378 - 1.066 = 0.312秒 - **这是音频末尾的静音！**

**结论：**
- WhisperX识别的字符时间戳只覆盖了**有语音的部分**（0-1.066秒）
- 但音频文件本身长度是1.378秒（包含末尾静音）
- 当前代码使用 `duration` (1.378秒) 作为实际时长
- 但字符时间戳只到1.066秒
- 导致字幕提前结束，后面的句子startTime也提前了

## ✅ 解决方案

### 方案A：使用最后字符的end时间（推荐）

```java
// ❌ 错误：使用duration（包含末尾静音）
double actualSpeechDuration = whisperXChars.get(whisperXChars.size() - 1).getEndTime();

// ✅ 正确：使用最后字符的end时间（纯语音）
double actualSpeechDuration = whisperXChars.get(whisperXChars.size() - 1).getEndTime();
```

**等等，代码已经是这样的了！**

**可能的问题：**

### 问题1：最终音频合并时的停顿不准确

```java
// 步骤6: 合并音频片段
byte[] finalAudio = audioMerger.merge(audioSegments, voiceConfig.getSampleRate());
```

这里的 `merge()` 会添加停顿，但停顿的时长可能与计算的不一致。

### 问题2：TTS生成的音频本身有问题

TTS引擎生成的音频可能在开头或结尾有额外的静音。

### 问题3：视频编码时引入的延迟

MP4编码时可能引入音视频同步偏差。
